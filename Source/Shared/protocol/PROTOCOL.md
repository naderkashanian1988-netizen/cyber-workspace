# CYBER-PROTOCOL v1

Shared wire protocol between the **CYBER WORKSPACE** Windows host and paired
Android remotes. Version constant: `protocol_version = 1`.

Status of this document: implemented by `Source/Windows/cyber_workspace/remote/` and
`android/` in this repository.

---

## 1. Transport

| Property | Value |
| --- | --- |
| Transport | TCP, newline-delimited JSON (NDJSON, UTF-8, one message per `\n`) |
| Encryption | TLS 1.3 (fallback TLS 1.2), server-side self-signed certificate generated on first run |
| Server auth | Certificate SHA-256 fingerprint is displayed (and QR-encoded) on the desktop at pairing time; the Android client pins that fingerprint |
| Client auth | Per-device token issued during pairing; sent as `auth` message after TCP connect |
| Default port | `47701` (configurable) |
| Discovery | mDNS service `_cyberworkspace._tcp.local.` advertising host name + port (informational only; pairing always requires the PIN) |
| Limits | Max message size 1 MiB. Idle session timeout 10 minutes. Max 30 messages/second per connection. |

## 2. Message envelope

Every message is a JSON object:

```json
{
  "v": 1,
  "id": "b3c1d2e4-...",
  "type": "snapshot",
  "ts": 1730000000000,
  "payload": { }
}
```

- `v` — protocol version integer.
- `id` — UUID string, generated by the sender.
- `type` — one of the message types below.
- `ts` — sender epoch milliseconds.
- `payload` — object; type-specific.

Unknown `type` ⇒ server replies with `error{code:"unknown_type"}`.
Unknown `v` greater than supported ⇒ `error{code:"unsupported_version"}`.

## 3. Message types

### Client → server

| type | payload | notes |
| --- | --- | --- |
| `hello` | `{client_name, client_platform, protocol_version}` | first message after connect |
| `pair_request` | `{pin}` | 6-digit numeric PIN shown on the desktop; PIN is single-session, 5-minute TTL, 5 attempts max |
| `auth` | `{device_id, token}` | after pairing, or on reconnect |
| `subscribe` | `{}` | start receiving `task_event` / `notification` pushes |
| `get_snapshot` | `{}` | full workspace snapshot |
| `get_task` | `{task_id}` | one task card + recent log lines |
| `get_logs` | `{task_id, max_lines}` | task log tail |
| `command` | `{task_id, action, params?}` | `action` ∈ `pause` `resume` `restart` `approve` `close` `open_details` |
| `approve` | `{request_id, decision}` | `decision` ∈ `approve` `deny` — answers a user-approval request |
| `list_devices` | `{}` | paired devices of this account (view only) |
| `ping` | `{}` | keep-alive |
| `revoke_self` | `{}` | device unregisters itself |

### Server → client

| type | payload | notes |
| --- | --- | --- |
| `welcome` | `{protocol_version, workspace_name, engine_version, features[]}` | reply to `hello` |
| `pair_result` | `{ok, device_id?, token?, cert_fingerprint?, error?}` | token is shown **once** |
| `auth_result` | `{ok, scopes[], error?, session_expires_s}` | |
| `snapshot` | `{generated_at, system, tasks[]}` | see structures below |
| `task_event` | `{event_type, task_id, task}` | `event_type` ∈ `state_changed` `metrics` `progress` `removed` |
| `notification` | `{id, severity, task_id, code, title, body, actions[], ts}` | `severity` ∈ `info` `warning` `critical` |
| `command_result` | `{ok, action, task_id, error?}` | |
| `logs` | `{task_id, lines[]}` | |
| `devices` | `{devices[]}` | |
| `pong` | `{}` | |
| `error` | `{code, message?}` | `code` ∈ `unknown_type` `unsupported_version` `unauthorized` `bad_pin` `rate_limited` `bad_request` `not_found` `internal` |

## 4. Data structures

### TaskCard

```json
{
  "id": "uuid",
  "name": "Ingest job",
  "adapter": "python",
  "state": "RUNNING",
  "state_reason": "",
  "pid": 41232,
  "progress": {"text": "3/10 files", "pct": 30.0},
  "last_activity_ms": 1730000000000,
  "timers": {"active_s": 120.5, "waiting_s": 30.0, "error_s": 0.0,
             "unknown_s": 5.0, "elapsed_s": 190.0},
  "metrics": {"cpu_percent": 3.2, "ram_mb": 148.6, "net": null},
  "approval_pending": null
}
```

`approval_pending` is non-null while the task is `WAITING_FOR_USER`:

```json
{"request_id": "uuid", "summary": "Approve license agreement?"}
```

`metrics.net` is `null` in v1 (per-process network accounting is not reliably
available on Windows without kernel tracing). Clients must render it as
"unavailable", never as 0.

### system

```json
{
  "cpu_percent": 41.0,
  "ram_percent": 62.3,
  "net_down_bps": 184213.0,
  "net_up_bps": 9511.0,
  "latency_ms": 23.5,
  "online": true,
  "keep_awake": {"enabled": true, "justified_by_tasks": 2}
}
```

## 5. Pairing sequence

```
Android                          Windows
  |-- hello ----------------------->|
  |<------ welcome -----------------|
  |-- pair_request {pin} ---------->|   (PIN from desktop pairing dialog, 5 min TTL)
  |<------ pair_result {token} -----|   (stored in EncryptedSharedPreferences; token shown once)
  |-- auth {device_id, token} ----->|
  |<------ auth_result {scopes} ----|
  |-- subscribe ------------------->|
  |<------ snapshot ----------------|
  |<------ task_event / notif ------|   (pushed while subscribed)
```

Rejection rules: 5 wrong PIN attempts invalidate the pairing session; tokens
are stored server-side only as SHA-256 hashes and can be revoked per device;
revoked devices receive `unauthorized` and the socket is closed.

## 6. Scope / access control

Pairing grants the scopes: `view`, `approve`, `control`.
- `view` — snapshots, logs, notifications.
- `approve` — answer `WAITING_FOR_USER` requests.
- `control` — pause / resume / restart / close tasks.

Remote **task creation** is deliberately not part of v1: creating tasks from a
remote device is disabled unless a future version introduces explicit
server-side consent per command.

Every authenticated mutating command is written to the server-side audit log.

## 7. Versioning & compatibility

- `hello` is mandatory and is the compatibility gate.
- Adding optional payload fields is a minor change (no version bump).
- New message types or semantic changes bump `protocol_version`; the server
  keeps supporting the previous version for one major cycle.
